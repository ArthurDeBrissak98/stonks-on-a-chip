# LIMITS-EXPERIMENT-PLAN: поиск физических пределов STM32H723ZG

- **Статус:** Planning phase (hardware pending purchase)
- **Дата:** 2026-11-11
- **Область:** измерения, не firmware. Код будет отдельной задачей.
- **Платформа:** NUCLEO-H723ZG, Cortex-M7 @ 550 MHz, 64 KB ITCM / 128 KB DTCM,
  32 KB L1 I/D ([ADR-001](ADR-001-mcu-selection.md))
- **Транспорт:** SPI @ 50 MHz, UART как отладочный канал ([ADR-002](ADR-002-transport-strategy.md))

---

## 0. Общие правила измерения

Эти правила применяются ко **всем** разделам ниже. Нарушение любого из них
делает результат недействительным.

### 0.1 Единый инструмент времени

Все замеры времени выполняются по `DWT->CYCCNT`. Перевод в наносекунды:
`ns = cycles × 1.818` при 550 MHz.

Обязательные условия корректности:

- `DWT->CTRL` — включены `CYCCNTENA` и бит доступа к трассировке
  (`TRCENA` в `DEMCR`). Без этого счётчик не тикает молча.
- **`CYCCNT` не останавливается в halt-режиме отладчика.** Если исполнение
  остановлено точкой останова, счётчик продолжает идти. Любой замер,
  сделанный через остановку в отладчике, недействителен.
- Измерение должно читаться **до** и **после** участка без иных обращений
  к DWT между ними.

### 0.2 Регистрация условий прогона

Каждый прогон фиксирует: частоту ядра, состояние I-кэша и D-кэша, состояние
ART/prefetch, размещение горячего кода (ITCM / flash / AXI SRAM), размещение
данных (DTCM / SRAM / SDRAM), версию Zephyr, конфигурацию сборки
(`prj.conf`, схема линковки). Без этого набор цифр невоспроизводим.

### 0.3 Статистика, а не одно число

Для латентностей фиксируются **p50, p90, p99, p99.9, max** и число
измерений `n`. Одного среднего недостаточно: цель проекта — найти хвост
распределения, а не его центр.

### 0.4 Как фиксируются результаты

Единый формат: CSV на прогон + markdown-сводка. Колонки CSV:
`run_id, section, config, metric, value, unit, n, notes`.
Сырые CSVs складываются рядом с отчётом; отчёт ссылается на файлы, а не
пересказывает их. Каждая сводка обязана содержать условие из §0.2 и
указание, был ли активен overflow-учёт (§0.5).

### 0.5 Обработка переполнения DWT CYCCNT

**Это обязательный элемент всех разделов, а не отдельный эксперимент.**

`DWT->CYCCNT` — 32-битный. При 550 MHz он переполняется каждые

```
2^32 / 550 000 000 = 7.8095 с
```

Практические следствия:

| Длительность прогона | Что происходит | Действие |
|---|---|---|
| < 1 с | Переполнение маловероятно | Прямая разность `t1 - t0` допустима **только** если гарантировано `t1 >= t0` по модулю |
| 1–7.8 с | Возможно одно переполнение | Обязателен overflow-учёт |
| > 7.8 с | Гарантированно ≥1 переполнение | Overflow-учёт обязателен; без него числа — мусор |

**Метод overflow-учёта (wrap-safe разность).** Разность считается в
`uint32_t` с естественным переполнением:

```c
uint32_t delta = (uint32_t)(t_end - t_start);   /* корректно при < 7.81 с между отсчётами */
```

Это работает при условии, что между двумя отсчётами прошло **меньше**
`2^32` циклов. Для интервалов, которые могут превысить 7.81 с, добавляется
**программный счётчик старших разрядов**:

- Периферийный таймер (например, 32-битный TIM) с периодом заведомо меньше
  7.81 с вызывает прерывание и инкрементирует 64-битный счётчик эпох.
- Итоговое время = `epochs × 2^32 + CYCCNT`.
- Альтернатива: считать общее время по 32-битному аппаратному таймеру, а DWT
  использовать только для коротких интервалов (< 7.81 с), где wrap-safe
  разность достаточна.

**Проверка, что учёт работает.** Обязательный тест: прогон длительностью
**> 30 с** (не менее 4 переполнений) с независимым контролем общего времени
по внешнему секундомеру или по host-side метке. Расхождение > 0.01 %
означает ошибку учёта, и все длинные прогоны в этом наборе недействительны.

**Отдельно:** в Разделе 5 (длительные прогоны под нагрузкой) наивный
`t_end - t_start` без overflow-учёта даёт **произвольный** результат. Это
самая вероятная ошибка всего плана.

### 0.6 Baseline-валидация

Перед любым содержательным замером выполняется Раздел 1. Если Baseline не
сходится, остальные разделы не запускаются.

## 1. Baseline: blink + замер пустого цикла

**Цель:** доказать, что мы умеем измерять время, и получить опорную точку,
относительно которой считаются все накладные расходы.

### Гипотеза

При корректно включённом DWT разность `CYCCNT` на пустом участке кода
стабильна и воспроизводима, а её распределение имеет пренебрежимо малый
хвост. Если хвост велик — инструмент измерения ненадёжен, и все дальнейшие
цифры недостоверны.

### Метод измерения

1. **Blink как доказательство жизни.** GPIO toggling с частотой, измеряемой
   осциллографом/логическим анализатором. Это внешняя, независимая от MCU
   проверка: частота переключения подтверждает фактическую частоту ядра.
   Целевая частота ядра 550 MHz проверяется именно здесь, а не принимается
   на веру.
2. **Пустой цикл.** Участок из N повторов минимальной операции
   (например, инкремент регистра или `nop`), обрамлённый двумя чтениями
   `CYCCNT`. N выбирается так, чтобы суммарное время было заведомо меньше
   7.81 с (например, N = 10^6).
3. Прогонов — не менее 1000; N подбирается так, чтобы измеряемая величина
   многократно превышала стоимость самих чтений DWT.
4. Снять распределение `delta`, а не только среднее.

### Ожидаемый результат

- Средняя стоимость итерации — единицы циклов, стабильно.
- p99.9 превышает p50 незначительно (в идеале — в разы меньше, чем 2x).
- Накладные расходы двух чтений `CYCCNT` измеримы и вычитаемы.

Ожидаемые ориентиры (подлежат подтверждению замером, **не** критерии приёмки):
при 550 MHz один цикл = 1.818 нс; участок из 10^6 итераций по 1 циклу
≈ 1.82 мс, что на 3 порядка меньше периода переполнения.

### Как фиксируется

- CSV с полным распределением `delta` для каждого N.
- Отдельная строка с измеренной накладной стоимостью пары чтений DWT.
- Сводка: подтверждённая частота ядра (по осциллографу), распределение
  пустого цикла, вывод о пригодности инструмента.
- **Артефакт-шлюз:** подписанный вывод «инструмент валиден / не валиден».
  Пока он не получен, Разделы 2–5 не запускаются.

## 2. Транспорт: UART → SPI → максимум

**Цель:** найти точку, где транспорт перестаёт успевать, и убедиться, что
она лежит выше точки, где упирается CPU.

### Гипотеза

На UART 12 Mbit/s канал насыщается раньше CPU и до потери тиков дело не
доходит — узкое место транспорт. На SPI 50 MHz запас достаточен, чтобы
узким местом стал CPU. Существует частота SPI, выше которой начинаются
потери, и она определяется целостностью сигнала, а не логикой.

### Метод измерения

Три последовательные ступени, каждая с одинаковой нагрузкой (одинаковая
частота тиков и одинаковая стратегия):

1. **UART @ 12 Mbit/s.** Измеряется фактическая полезная скорость
   (байт/с), доля CPU на обработку передачи, число потерянных байт.
   Ожидание: ~1.2 MB/s полезной нагрузки при кадрировании 8N1.
2. **SPI @ 50 MHz.** Измеряется фактическая полезная скорость
   (ожидание ~5.6 MB/s при КПД ~90 %), доля CPU на DMA-обслуживание,
   число потерянных пакетов.
3. **SPI на максимуме.** Частота повышается ступенями до появления ошибок
   целостности (CRC-ошибки, потеря пакетов). Фиксируется максимальная
   устойчивая частота.

Для каждой ступени:

- Передаётся фиксированный объём данных (например, 100 MB), замеряется
  время по DWT с overflow-учётом (§0.5) и/или по хосту.
- Одновременно снимается CPU% (см. Раздел 3) для ответа на вопрос
  «транспорт или CPU?».
- Проверяется целостность: CRC/счётчик последовательности, число
  потерянных и повреждённых пакетов.

### Ожидаемый результат

| Ступень | Ожидаемая полезная скорость | Ожидаемое узкое место |
|---|---|---|
| UART 12 Mbit/s | ~1.2 MB/s | транспорт |
| SPI 50 MHz | ~5.6 MB/s | CPU |
| SPI max | выше 6.25 MB/s сырых | целостность сигнала |

Ключевой ожидаемый вывод: **переход UART → SPI смещает узкое место с
транспорта на CPU**. Это и есть обоснование [ADR-002](ADR-002-transport-strategy.md).

### Как фиксируется

- Таблица «частота → полезная скорость → CPU% → потери».
- Отдельно фиксируется максимальная устойчивая частота SPI и признак,
  по которому зафиксирован отказ (CRC, потеря пакетов, ошибка DMA).
- Скриншоты/декодирование логического анализатора для максимальной частоты —
  доказательство, что ошибки именно целостности, а не логики.
- **Обязательно:** проверка кэш-когерентности при DMA. Если буферы SPI
  размещены в кэшируемой памяти, отдельно фиксируется, применялись ли
  clean/invalidate. Ошибки когерентности выглядят как «случайная порча
  данных» и легко принимаются за проблемы сигнала.

## 3. CPU: SMA → сложная стратегия → замер CPU%

**Цель:** найти предел вычислителя — сколько тиков в секунду стратегия
успевает обработать до потери тиков.

### Гипотеза

По мере усложнения стратегии CPU% растёт линейно до точки, где обработчик
перестаёт укладываться в бюджет тика; после этой точки начинаются потери
тиков, и латентность растёт нелинейно. Простая стратегия (SMA) не является
пределом — запас есть.

### Метод измерения

Три уровня сложности стратегии на одном и том же транспорте и одной частоте
тиков:

1. **SMA** — минимальная арифметика, baseline вычислительной стоимости.
2. **Сложная стратегия** — например, несколько индикаторов с плавающей
   точкой/фиксированной точкой, сортировка окна, ветвления по состоянию.
   Наличие FPU (Cortex-M7 с FPU) позволяет сравнить float и fixed-point
   как отдельную под-гипотезу.
3. **Насыщение** — частота тиков повышается до появления потерь.

Что измеряется:

- **CPU%** — доступными средствами: счётчик загрузки планировщика Zephyr
  (`k_thread_runtime_stats` / thread runtime statistics) плюс независимая
  проверка по DWT (суммарное время в обработчике / общее время).
  Расхождение двух методов — само по себе результат.
- **Латентность обработки одного тика** — полное распределение по DWT.
- **Потеря тиков** — счётчик пропущенных срабатываний относительно
  источника тиков.
- Раздельно измеряется время в обработчике и время вне его
  (планировщик, переключения контекста, прерывания транспорта).

Конфигурации, между которыми проводится сравнение (каждая — отдельный набор):

- горячий код в ITCM vs во flash/AXI SRAM;
- данные в DTCM vs в SRAM;
- I-кэш вкл/выкл, D-кэш вкл/выкл;
- float vs fixed-point.

### Ожидаемый результат

- CPU% монотонно растёт с частотой тиков и сложностью стратегии; точка
  излома соответствует пределу.
- Код/данные в TCM дают заметно меньший и, главное, **более узкий** хвост
  латентности, чем код/данные в кэшируемой памяти.
- Отключение кэша при работе из flash даёт резкий рост средней латентности.
- Ожидаемая граница: при 550 MHz бюджет 1M тиков/с составляет **550 циклов
  на тик** — стратегия сложнее ~550 циклов физически не уложится в 1M тиков/с.

### Как фиксируется

- Матрица «стратегия × размещение × кэш → CPU%, p50, p99.9, потери».
- График зависимости латентности от частоты тиков с явно отмеченной точкой
  излома.
- Раздельные цифры «время в обработчике» и «время вне обработчика».
- Сравнение CPU% по двум независимым методам с указанием расхождения.

## 4. Память: DTCM vs SRAM vs SDRAM — замер латентности

**Цель:** измерить латентность доступа к каждой области памяти и увидеть,
во сколько раз кэш и внешняя память ухудшают предсказуемость.

### Гипотеза

Латентность доступа монотонно растёт в порядке DTCM < SRAM (AXI) < SDRAM,
причём у SDRAM разброс (хвост) значительно больше, чем у TCM. Кэш сглаживает
среднее, но увеличивает худший случай при промахах — то есть улучшает
p50 и ухудшает p99.9.

### Метод измерения

Один и тот же шаблон доступа (последовательный проход по массиву с известным
шагом, циклически, чтобы исключить влияние однократного прогрева) применяется
к массивам, размещённым в разных областях:

| Область | Расположение на H723 | Ожидаемый характер |
|---|---|---|
| DTCM | 128 KB @ `0x20000000` | минимальная, детерминированная |
| ITCM | 64 KB @ `0x00000000` | для кода |
| AXI SRAM | 320 KB @ `0x24000000` | средняя, кэшируемая |
| AHB SRAM (D2/D3) | SRAM1/2/4, по 16 KB | средняя, другой домен |
| SDRAM (внешняя, через FMC) | если подключена | максимальная, широкий хвост |

Для каждого варианта:

- Замер латентности отдельной операции чтения/записи по DWT
  (при необходимости — с вычитанием накладных расходов из Раздела 1).
- Замер при **включённом** и **выключенном** D-кэше.
- Размер массива варьируется: заведомо меньше кэша (полное попадание) и
  заведомо больше кэша (гарантированные промахи). Это разделяет «латентность
  памяти» и «латентность кэша».
- Распределение, а не среднее: p50/p90/p99/p99.9/max.

### Ожидаемый результат

- DTCM: стабильная низкая латентность, узкий хвост, практически не зависит
  от состояния кэша.
- SRAM/AXI: средняя латентность выше DTCM; с кэшем p50 улучшается, p99.9
  может ухудшаться из-за промахов.
- SDRAM: самый широкий хвост; при большом рабочем наборе p99.9 заметно
  превышает p50.

Ожидаемый вывод: **для детерминированной латентности горячий путь обязан
жить в TCM**, а кэш следует рассматривать как источник вариативности, а не
только ускорения. Это согласуется с последствиями [ADR-001](ADR-001-mcu-selection.md).

### Как фиксируется

- Таблица «область × состояние кэша × размер набора → p50/p99/p99.9/max».
- Явное указание, был ли SDRAM подключён. Если SDRAM на плате отсутствует,
  строка помечается «не измерено» — **не** подставляется значение из
  документации.
- Отдельная фиксация отношения p99.9/p50 по каждой области — это входной
  параметр для критериев §6.

## 5. Джиттер под нагрузкой: до 1M тиков/с

**Цель:** найти предел по частоте тиков, при котором система сохраняет
предсказуемость, и увидеть, как растёт хвост распределения.

### Гипотеза

При росте частоты тиков до 1M тиков/с джиттер сначала остаётся в пределах
нескольких процентов, затем вблизи предела резко растёт. Существует частота,
выше которой p99.9 превышает 2x p50 — это и есть практический предел
предсказуемости. Источник джиттера вблизи предела — не CPU, а конфликты
доступа к памяти и прерывания транспорта.

### Метод измерения

- **Источник тиков** — аппаратный таймер (не программный цикл), чтобы
  нагрузка не зависела от точности планировщика.
- Частота тиков повышается ступенями: например 1k → 10k → 100k → 500k → 1M
  тиков/с. На каждой ступени — прогон достаточной длительности
  (заведомо **> 7.81 с**, то есть с обязательным overflow-учётом; для
  надёжности — минуты).
- **Джиттер** определяется как отклонение фактического времени обработки
  тика (или интервала между тиками) от ожидаемого: `jitter = t_actual − t_expected`.
  Фиксируется полное распределение.
- Нагрузка варьируется независимо: (а) только генерация тиков;
  (б) тики + активный транспорт (SPI на рабочей частоте);
  (в) тики + транспорт + стратегия. Это разделяет вклад источников.
- Отдельно: прогон с искусственно добавленным прерыванием высокой частоты —
  проверка чувствительности к вытеснению.

Важно: при 550 MHz и 1M тиков/с бюджет составляет **550 циклов на тик**.
Вход и выход из прерывания, вызов обработчика и доступ к памяти съедают
изрядную часть этого бюджета, поэтому 1M тиков/с — реалистичная, но
напряжённая верхняя граница.

### Ожидаемый результат

| Частота тиков | Бюджет (циклов/тик) | Ожидаемое поведение |
|---|---|---|
| 1k | 550 000 | джиттер в пределах шума измерения |
| 10k | 55 000 | стабильно |
| 100k | 5 500 | лёгкий рост хвоста |
| 500k | 1 100 | заметный рост p99.9 |
| 1M | 550 | предел близко; возможны потери |

Ожидается, что добавление транспорта и стратегии сдвигает точку роста
хвоста вниз, а размещение горячего пути в TCM — вверх.

### Как фиксируется

- Для каждой частоты: p50/p99/p99.9/max джиттера, число потерянных тиков,
  CPU%, отношение p99.9/p50.
- Явная отметка, был ли активен overflow-учёт (§0.5) и результат
  контрольного прогона > 30 с.
- График «частота тиков → p99.9» с отмеченной точкой, где нарушен критерий.
- Разделение прогонов по составу нагрузки, чтобы был виден вклад транспорта.

## 6. Criteria for "limit reached"

Предел считается **достигнутым**, когда выполнено **любое** из условий ниже
(при условии, что Baseline из Раздела 1 валиден и overflow-учёт подтверждён
контрольным прогоном). Условия намеренно количественные, чтобы результат не
зависел от интерпретации.

| # | Критерий | Порог | Что означает |
|---|---|---|---|
| **L1** | Отношение хвоста латентности | **p99.9 > 2 × p50** | Предсказуемость потеряна: редкие, но регулярные выбросы вдвое хуже типичного случая |
| **L2** | Потеря тиков | **> 0.01 %** от сгенерированных | Система физически не успевает обрабатывать вход |
| **L3** | Джиттер | **p99.9 джиттера > 1 × бюджет тика** | Выбросы джиттера превышают весь бюджет одного тика |
| **L4** | Насыщение транспорта | полезная скорость перестала расти при повышении частоты SPI **и** появились ошибки целостности | Упёрлись в физику линии, а не в логику |
| **L5** | CPU | **CPU% ≥ 95 %** на целевом профиле нагрузки устойчиво | Вычислитель исчерпан |
| **L6** | Расхождение методов измерения | CPU% по планировщику и по DWT расходятся **> 5 %** | Инструмент измерения перестал быть достоверным; результат раздела недействителен |

Дополнительные правила применения:

- **Лимит фиксируется по первой нарушенной границе** в порядке возрастания
  нагрузки, а не по самому красивому числу из серии.
- Критерии **L1–L3** относятся к латентности и джиттеру; **L4** — к
  транспорту; **L5** — к CPU; **L6** — к достоверности инструмента.
- Если нарушен **L6**, раздел переизмеряется, а не интерпретируется.
- Границы считаются достигнутыми **устойчиво**: критерий должен
  воспроизводиться не менее чем в **3 независимых прогонах**. Единичный
  выброс не является достижением предела.
- Все пороги — **гипотезы до первого прогона**. Порог, изменённый после
  получения данных, фиксируется отдельно с обоснованием; молчаливая
  подгонка порога под результат запрещена.

### Что считается результатом проекта

Итог v2 — не «мы достигли предела», а **карта пределов**: для каждой из
пяти осей (транспорт, CPU, память, джиттер, латентность) известна
нагрузка, при которой нарушается соответствующий критерий, и известно,
какой ресурс является узким местом. Эта карта и есть основание для решения
о переходе на следующий уровень (Ethernet, kernel bypass, FPGA): переход
оправдан, когда узкое место лежит **вне** исследуемого кремния.
